# Operação do worker

Contexto Docker: backend/. Build: `docker build -t pcdnades-worker:local backend` a partir da raiz. Imagem usa Node22, FFmpeg/ffprobe Debian e usuário não root; não inclui .env ou arquivos MP4. Build baixa imagens/pacotes, não toca Supabase. Para repetibilidade estrita, fixar digest da imagem após validação pelo operador.

Execução: `docker run --rm --init --read-only --tmpfs /tmp:rw,noexec,nosuid,size=256m --memory=1g --cpus=1 --env-file /caminho/seguro/worker.env pcdnades-worker:local`. Arquivo env fora do Git, permissões só para operador. Não passar valores secretos na linha de comando/log/chat. CPU/RAM/tmp são limites iniciais a validar com arquivos reais de até20s/50MB. Não expor portas; container executa batch e termina quando fila esvazia.

Env obrigatórias: DATABASE_URL (conexão PostgreSQL com papel servidor autorizado ao schema público/worker e TLS validado), SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY. MEDIA_MAX_BYTES e MEDIA_MAX_DURATION_SECONDS iguais à API, teto20s. Não precisa publishable key, FRONTEND_URL ou PORT. Não usar DATABASE_URL do navegador. Configuração da rede/Supabase e credenciais são responsabilidade do operador; não desabilitar verificação TLS para contornar conexão.

Caminho simples para time pequeno: um único job Docker agendado a cada minuto num host de containers existente ou pequeno servidor dedicado, com segredo gerenciado e no máximo uma execução ativa; evitar novo Redis/fila externa porque PostgreSQL já persiste a fila. Esta é uma proposta operacional, host/custo ainda não aprovados. Scheduler deve pular disparo se anterior estiver ativo, registrar código de saída/alerta e impor janela suficiente para esvaziar a fila. Não matar cada minuto: job individual pode levar até10 minutos. A API Vercel não executa este worker e não deve chamar FFmpeg.

Ao parar/reiniciar, jobs processing só voltam à fila após lease de15min; máximo3 tentativas e depois failed. Erros de conteúdo viram failed; fila vazia termina com sucesso. Não interpretar código0 como prova de processamento de todos arquivos: consultar estados failed e logs. Nenhum endpoint público para iniciar worker. Logs não devem incluir URL assinada/credenciais.

Fontes/saídas sem referência ainda precisam reconciliação e política de retenção, não estão automaticamente apagadas; acompanhar uso de Storage. Cancelamento do host pode deixar temporários no container descartado e objetos órfãos no Storage. Antes de produção exercitar retomada, limite de quota, erros reais, upload/reprodução e monitoramento.

Teste independente de mídia: `node backend/scripts/media-smoke.mjs` (ou dentro de backend: `node scripts/media-smoke.mjs`). Requer ffmpeg/ffprobe já no PATH; gera fixture sintética azul com seno2s, converte com opções do worker e verifica h264/aac, duração, bytes e ordem moov/mdat. Remove temporários no finally. Não executa worker completo, SQL, rede ou Supabase; não prova integração Storage. Não instala dependências do sistema.

## Proposta de execução automática fora do PC (aguarda decisão)
Recomendação técnica: **Render Cron Job Docker** para o batch atual. Não exige transformar worker em daemon nem expor HTTP, permite segredos no serviço e garante uma execução ativa. Job agendado aguarda execução anterior; Trigger Run manual cancela a ativa, portanto não usar durante processamento. Cron é UTC; intervalo inicial proposto */5 * * * *, reduzível após medir carga/tempo. Render tem mínimo mensal de US$1 por cron e cobrança adicional conforme compute/tempo: não é gratuito nem foi contratado. Confirmar custo/plano antes de criar. Referência consultada em29/10: https://render.com/docs/cronjobs .

Configuração concreta para operador após aprovação:
- Serviço Cron Job, runtime Docker; repositório Lipe-meira/pcdNades, branch main após integração; Root Directory backend, Dockerfile Dockerfile e contexto . (equivalentes na raiz: backend/Dockerfile, contexto backend).
- Schedule */5 * * * * UTC, CMD da imagem node dist/worker.js; sem Start Command do servidor/API, sem porta/health HTTP ou disco persistente.
- Selecionar CPU/memória após teste do limite real; 1GB/1CPU foi validado somente com fixture pequena, não é dimensionamento comprovado para50MB/20s. Temporários efêmeros são suficientes; banco/Storage persistem fora do container.
- Criar variáveis secretas DATABASE_URL e SUPABASE_SERVICE_ROLE_KEY direto no host; SUPABASE_URL e limites 50000000/20. Validar caminho de rede PostgreSQL/TLS e permissões do papel. Não colocar valores em Blueprint, Git ou chat. Não incluir chave pública do frontend como substituta da service role.
- Primeiro executar uma vez com fila vazia, observar saída e depois upload de fixture autorizada por fluxo real coordenado. Só habilitar MEDIA_UPLOAD_ENABLED na API após confirmar queued->processing->ready, playback e falha controlada. Não confundir smoke local com aprovação de ativação.

Alternativa sem contrato pago novo: **GitHub Actions em runner hospedado** no repo público, se uso/cota/política da conta permitirem. Schedule mínimo5min, pode atrasar/ser descartado sob carga; runs agendados somente branch default e podem ser desabilitados após60dias sem atividade. Não atende garantia de processamento rápido/contínuo. Preferir minuto deslocado (por exemplo 2-57/5), concurrency exclusiva e cancel-in-progress false; timeout de job suficiente para múltiplos vídeos/lease. Secrets só em environment protegido e eventos schedule/workflow_dispatch confiáveis, nunca pull_request de fork. Propor GITHUB_TOKEN contents:read, checkout revisado/fixado e docker build/run com env do job sem imprimir valores, sem artefatos de env/log sensível. Criar YAML .github somente pelo orquestrador após escolha. Referência: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule .

Nenhuma opção inicia em tempo real quando um upload chega: UI precisa comunicar espera pela próxima execução e tempo de processamento. Requisito de baixa latência contínua exigiria worker daemon/serviço contínuo e nova decisão, não presumida para este batch. Proposta atual é periódica automática fora PC.
